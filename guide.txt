#### Separating creators by platform tabs
The creator tabs on `creators.html` filter by the creator row's `platform` field. If a creator only appears under **All**, it usually means the `platform` value is missing, misspelled, or does not exactly match a tab's `data-platform` value.

Use these exact `platform` string values in the `creators` table/collection:

| Tab button | Creator `platform` value |
| --- | --- |
| YouTube | `YouTube` |
| Twitter / X | `Twitter / X` |
| TikTok | `TikTok` |
| Instagram | `Instagram` |

Important rules:
- Use the field name `platform` (not `platforn`). The site still supports `platforn` only as an old typo fallback, but new creator rows should use `platform`.
- Platform matching is now case-insensitive, so `YouTube`, `Youtube`, `YOUTUBE`, and `youtube` all match the YouTube tab.
- Multiple platforms are supported by comma-separating values, for example `Youtube, Instagram`. That creator will appear under both the YouTube and Instagram filters.
- Spaces around comma-separated values are okay: `Youtube , Instagram` still works.
- The wording still needs to normalize to the same platform name after casing/spaces are ignored. For example, `You Tube` (with an internal space) and `IG` will not match the current `YouTube` / `Instagram` tabs.
- If you want another platform tab later (for example `LinkedIn`), add a new button in `creators.html` with `data-platform="LinkedIn"`, then use `platform = LinkedIn` in creator rows.
- After changing creator fields in Appwrite, refresh the page and clear session storage if old creator data is cached.

## 3) Cloudflare setup (cache bridge)

## 3.1 Create Worker + KV
1. In Cloudflare dashboard, create one Worker.
2. Create one KV namespace (and preview namespace).
3. Copy KV IDs into `cloudflare-worker/wrangler.toml`:
   - `id`
   - `preview_id`

## 3.2 Upload files to Cloudflare Worker project
From this repo, use the files exactly from:
- `cloudflare-worker/src/index.js`
- `cloudflare-worker/wrangler.toml`

If deploying with Wrangler locally:
```bash
cd cloudflare-worker
npm i -g wrangler
wrangler login
```

## 3.3 Set Worker secrets (IMPORTANT)
```bash
wrangler secret put APPWRITE_API_KEY
wrangler secret put REFRESH_TOKEN
```

- `APPWRITE_API_KEY`: server key from Appwrite (read access to DB).
- `REFRESH_TOKEN`: any strong random token you choose for manual refresh endpoint.

## 3.4 Verify env vars in `wrangler.toml`
Ensure these are correct:
- `APPWRITE_ENDPOINT`
- `APPWRITE_PROJECT_ID`
- `APPWRITE_DATABASE_ID`
- `APPWRITE_TOOLS_COLLECTION_ID`
- `CACHE_TTL_SECONDS` (default `259200`, i.e. 3 days)

## 3.5 Deploy Worker
```bash
wrangler deploy
```

## 3.6 Cron trigger
Already configured in `wrangler.toml`:
- `0 0 */3 * *` → refresh every 3 days at 00:00 UTC.

## 7) Common issues and fixes

### Creators page stuck on loading
- Check browser console.
- Check Worker/Appwrite response latency.
- Trigger manual refresh endpoint.

### Wrong category count on homepage
- Clear session storage and refresh.
- Ensure full tools dataset has valid `category` fields.

### Appwrite errors from Worker
- Re-check `APPWRITE_API_KEY` secret.
- Re-check DB/collection IDs in `wrangler.toml`.

=== Admin Panel CORS + API Key Notes (2026-05-05) ===
- What happened:
  - Admin UI started calling Appwrite Tables/Rows directly from browser with x-appwrite-key.
  - Browser preflight/CORS can block this, even when domains are added, because server API key flows are safer via backend.
- What can happen:
  - 'TypeError: Failed to fetch' in console.
  - 401 scope errors if key misses rows.read/rows.write.
- How to fight it:
  1) Use cache bridge endpoint for read-only listing (`/tools`, `/categories`, `/stats`).
  2) For create/update/delete, use a server-side proxy or Cloudflare worker endpoint that stores key in secrets (not browser).
  3) Ensure key has rows.read + rows.write on current DB/table model.
- What was fixed now:
  - Added clear CORS/preflight error messaging in admin script.
  - Added fallback: if direct Appwrite tools read fails, admin falls back to cache bridge `/tools` so listing still works.
  - Updated wording for modern scopes (rows.read/rows.write).

- Temporary change: admin panel now supports Appwrite Dev Key header (`x-appwrite-dev-key`) and includes a short-lived hardcoded default key for quick testing. Remove it before production.

## 9) Blog publishing workflow (after EVERY blog publish)

### 9.1 Required Appwrite `blogs` fields
Each row in `blogs` collection must include:
- `slug`
- `title`
- `excerpt`
- `readTime`
- `publishedAt` (datetime)
- `path` (full URL, e.g. `https://m2zpicks.netlify.app/blogs/my-slug.html`)
- `category`
- `hero` (hero image URL for blog landing cards/featured block)

Allowed categories currently used on site:
- `Reviews`
- `Comparisons`
- `Rankings`
- `Guides`
- `News & Updates`
- `Alternatives`

### 9.2 After writing a new blog page
1. Create `blogs/<slug>.html` page.
2. Add one row in Appwrite `blogs` collection with matching `slug` + `path`.
3. Deploy to Netlify.
4. Trigger worker refresh (do not wait for daily cron):
```bash
curl -X POST "https://<your-worker>.workers.dev/refresh" \
  -H "x-refresh-token: <your_refresh_token>"
```

### 9.3 Verify data endpoints after refresh
Check these endpoints:
- `GET /blogs` should include your new row and all categories.
- `GET /blogs/latest` should place newest `publishedAt` first.
- `GET /blogs/categories` should show correct counts per category.

### 9.4 Verify frontend behavior
- Blogs landing page (`/blogs/index.html`) shows newest post in "Latest post".
- Category pages work:
  - `/blogs/category/Reviews`
  - `/blogs/category/Comparisons`
  - `/blogs/category/Rankings`
  - `/blogs/category/Guides`
  - `/blogs/category/News%20%26%20Updates`
  - `/blogs/category/Alternatives`
- Open the new blog page and confirm:
  - header/footer render
  - author section renders
  - related posts block loads
